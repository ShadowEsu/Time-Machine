A save point

            
Made before each prompt, before a risky shell command and after each agent turn. Your files, index and branch stay as they are.

            
    
              
  1. Your project: tracked files with edits you have not committed, and new files Git does not track yet.
    2. 
              
  2. A commit pinned at refs/tm/cp-0004, made through a temporary Git index.
    3. 
              
  3. Files Git does not track, stored as SHA-256 named, gzipped, read-only blobs in objects/. Over 5 MB is skipped unless you raise the limit.
    4. 
              
  4. The manifest checkpoints/cp-0004.json, written once and sealed with HMAC-SHA256. The key never leaves your computer.
    5. 
              
  5. A Git bundle, bundles/cp-0004.bundle, so the save point survives the project folder being deleted.
    6. 
              
  6. Never stored: secret files such as .env and *.pem, and secret values. Config keys keep only a name and a fingerprint.
    7.

The check

            
Your own command runs on the save point in a temporary copy. Its exit code becomes the verdict.

            
    
              
  1. git worktree add --detach builds the save point in a temporary folder, removed afterwards. Your working copy, index and branch are not touched.
    2. 
              
  2. A clean environment, with PATH, HOME and a few more, plus CI=1. A 600 second timeout by default.
    3. 
              
  3. verify.setup, such as npm ci, runs first, with the network on.
    4. 
              
  4. Your verify.command, such as npm test. The network is allowed by default.
    5. 
              
  5. With network: deny, the command runs under sandbox-exec on macOS or bwrap / unshare on Linux. With no sandbox the verdict is BLOCKED, and the check does not run.
    6. 
              
  6. The verdict and tm’s exit code: PASS 0, FAIL 1, INCOMPLETE 2, BLOCKED 3, ERROR 4. Each one is signed and appended to verdicts.jsonl.
    7.

The rewind

            
The newest save point that passes comes back next to your work, never in place of it.

            
    
              
  1. Your current state is saved first, as a new save point: cp-0007 in the demo.
    2. 
              
  2. A local branch, tm/recover/cp-0003, at that save point’s commit.
    3. 
              
  3. A recovery copy in the folder next to yours, marigold-tips-recovered-cp-0003.
    4. 
              
  4. Your folder and your branch are not touched. Nothing is pushed, merged or deployed.
    5. 
              
  5. Undo removes the copy and the branch, only if neither has changed since. It never removes a save point.
    6. 
              
  6. Every report lists what did not come back: database contents, deployed versions and secret values.
    7.

What runs where

            
All of the above runs on your computer. Two optional features of the web app reach the internet, and only after you turn them on.

            
    
              
  1. Claude Code calls three hooks from .claude/settings.json: before each prompt, before a risky Bash command, and when its turn ends.
    2. 
              
  2. The tm CLI, the MCP server and tm ui call one engine, packages/core. The engine makes no network calls.
    3. 
              
  3. The store, ~/.timemachine, sits outside your project.
    4. 
              
  4. tm ui listens on 127.0.0.1 only. Your browser gets a random 32-byte token in the URL fragment, and the server checks Host and Origin.
    5. 
              
  5. Optional: Ask sends a short history summary to Google Gemini with your own key, never file contents or logs. Vercel deploy lookups only read.
    6. 
              
  6. This website is separate: Vercel functions and a Supabase database for the waitlist. Nothing on your computer calls it, and a license key is checked offline.
    7.

More than a commit comes back

      
A save point is a Git commit pinned under refs/tm, plus a Git bundle in a store outside your project, plus what Git alone would miss. Every recovery report lists both columns, in these words.

    

    

      

        
Comes back

        
    
          
  • Your code, with uncommitted edits. The commit is made from your working tree, so edits you had not committed yet are in it. Code at commit a1b2c3d
    • 
          
  • Files not in Git. New files you had not added yet, up to a size limit you set. 3 saved files
    • 
          
  • Config, by key name. Keys you allowlist come back with their values. Every other key is kept as its name and a fingerprint, so you can tell what changed without the value ever being stored. Config: PORT
    • 
          
  • Lockfiles. package-lock.json, pnpm-lock.yaml, yarn.lock, Cargo.lock and similar, even when your .gitignore skips them, checked byte for byte against their recorded digests. Dependencies: package-lock.json
    • 
          
  • Environment definition files. Dockerfile, docker-compose.yml, .devcontainer/devcontainer.json and similar when Git has them. Version pins like .nvmrc and .tool-versions also when ignored. All checked against their digests. Environment definition: Dockerfile, .nvmrc
    • 
          
  • A Git bundle in the store. Kept in ~/.timemachine, so the save point survives the project folder being deleted. Runtime versions such as Node and Git are recorded and shown in a compare, not restored.
    • 
        

      

      

        
Does not come back

        
    
          
  • Secret values. Values from config files like .env are never stored, not even on your own computer, only key names and a fingerprint. The report names the keys you set again by hand. Secret values in .env: STRIPE_SECRET_KEY
    • 
          
  • Files that look like secrets. An edited tracked file that looks like it holds a secret keeps its last committed version instead. A file named like a secrets file is not saved. .env.local is a secrets file by name, so it was not saved
    • 
          
  • Files your .gitignore skips. Folders like node_modules or build output, unless you ask for them. Files your .gitignore skips were not saved: dist
    • 
          
  • Database contents, deployed versions and external services. Emails sent, payments made, anything on a server. Databases, deployed versions and external services are not captured
    • 
        

      

    

    
Every report ends with the same line: Restored: code, captured files, config. Not restored: database, deployed version, secret values. An unchecked save point is shown as not checked, never as working.

Questions

      
Does it replace Git?
No. It works next to Git. A recovery is a new branch you inspect before you merge it yourself.

      
Why not the agent’s own rewind?
Claude Code’s docs say rewind leaves a file as it is when only Bash commands changed it. Read the Claude Code docs

      
Does a PASS mean my app is correct?
It means your tests passed. Time Machine never calls a save point working unless your own check passed on it.

      
What happens after I join?
Your email goes on the list. This site sends no email; we write to the list ourselves when the CLI is on npm. If the form says the list isn’t open yet, email preston@unvibe.site instead.

      
Is the web app hosted?
No. tm ui runs on your computer. Your browser talks to it on 127.0.0.1 with a private token that changes each time you start it. Your project is never uploaded, and nothing on it needs a password.

      
What does the $50 buy?
A license key that lets the web app list as many projects as you like, instead of 3 at a time, on any number of your own computers, with updates while we ship them. One payment, no subscription. Paste the key in tm ui under Settings, then License, or run tm license <key>. The tm command line tool is open source (MIT) and stays that way, and restores are never behind the paywall. Checkout is not open yet, so nothing is for sale today.
