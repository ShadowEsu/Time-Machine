git bisect or tm find-good: which one finds your last working version

They sound alike and answer different questions. One finds the change that broke it. The other finds a version you can go back to.

TMThe Time Machine team

000%

Your tests passed this morning. Now they fail, and an agent made twenty changes in between. There are two questions you could ask. Which change broke it? And which version can I go back to right now? git bisect answers the first. tm find-good answers the second.

git bisect: find the change that broke it

git bisect does a binary search through your commits. You tell it one commit that is bad and one that is good. It checks out a commit halfway between them, you test it, and it halves the range again until it names the first bad commit. With a script it runs by itself:

$ git bisect start HEAD HEAD~20
$ git bisect run npm test
$ git bisect reset

Your script exits 0 for good and 1 to 127 for bad. Exit 125 means "this commit cannot be tested, skip it", for example when it does not build. Twenty commits take about five test runs, because each run halves the range.

Three things to know before you start:

  • It only sees commits. Work you never committed is not in the search.
  • It checks the commits out in your working folder, so you start from a clean folder and run git bisect reset at the end to get back.
  • You need a commit you know is good. If you are not sure, you guess, and a wrong guess sends the search the wrong way.

When those hold, it is the right tool. The commit it names tells you exactly what to fix.

tm find-good: find a version you can go back to

tm find-good starts from the newest save point and walks back, one at a time, until your check passes. Each save point is rebuilt in a separate Git worktree, so your folder and current branch stay as they are:

$ tm find-good
  cp-0006   FAIL       The check failed with exit code 1.
  cp-0005   FAIL       The check failed with exit code 1.
  cp-0004   FAIL       The check failed with exit code 1.
  cp-0003   PASS       The check passed.
PASS  cp-0003 is the newest version that works.

Then tm recover cp-0003 puts that version on a new branch, tm/recover/cp-0003, with a recovery copy next to your project. Nothing is pushed, merged or deployed.

It walks newest first instead of halving, because the newest version that works is the one you lose the least by going back to. It keeps going past a failed check and stops at the first pass. It also stops if the check cannot run yet, for example when no check command is set, and tells you why.

Save points are not commits. With the Claude Code hooks installed, Time Machine saves before each prompt if something changed, before risky shell commands, and at the end of each turn. Each save point includes uncommitted changes and files not in Git yet. So the version that worked at 10:40 is there even if nobody committed at 10:40.

The limit is the same in reverse: tm find-good only knows the moments Time Machine saved. It also tells you which version works, not why the next one broke.

Which one to use

  • You need to keep working now. Run tm find-good, recover, and carry on from a version that passes.
  • You need to know what broke it. Run git bisect between the save point that passed and the one that failed.
  • Both. Recover first, then bisect at leisure. tm diff cp-0003 cp-0004 often shows the cause without a bisect at all.

Neither one brings back a database a migration changed, a deploy that went out, or the values in your .env file. Time Machine lists what it did not restore on every recovery report.
